# Основные правила обучения

## 1. Один этап за один запрос

Не нужно пытаться объяснить сразу весь PostgreSQL, SQLAlchemy или Alembic.

За один запрос изучаем только одну тему или выполняем один небольшой
законченный шаг. Например:

- реляционная таблица;
- primary key;
- foreign key;
- один тип связи;
- один SQL-запрос с `JOIN`;
- настройка асинхронного engine;
- одна модель SQLAlchemy;
- одна миграция Alembic.

После объяснения и практики ждём моего сообщения «Дальше».

Если следующий шаг зависит от непонятого предыдущего шага, сначала нужно
устранить непонимание, а не двигаться дальше формально.

---

## 2. Практика важнее оторванной теории

Каждая тема должна применяться к текущему CRUD API.

Не нужно создавать отдельные игрушечные проекты и бессвязные таблицы. Мы
постепенно заменяем существующее временное хранилище:

```python
users_by_id: dict[UUID, UserRead]
```

на PostgreSQL.

В дальнейшем этот же проект должен получить ресурсы:

- users;
- organizations;
- dialogs;
- messages.

Именно на них нужно объяснять таблицы, связи, ключи, `JOIN`, ограничения,
индексы и ORM relationships.

## Главный текущий недостаток

Пользователи хранятся в оперативной памяти процесса:

```python
users_by_id: dict[UUID, UserRead] = {}
```

Из-за этого:

- все данные исчезают после перезапуска приложения;
- несколько процессов приложения не имеют общего состояния;
- проверка уникальности email не защищена от конкурентных запросов;
- фильтрация и пагинация происходят в Python;
- нет транзакций и гарантий целостности базы данных.

Практическая цель нового блока — постепенно заменить это хранилище на
PostgreSQL, не ломая без необходимости существующие маршруты и Pydantic-схемы.

# Практическая конечная цель блока

Заменить временное хранилище FastAPI-приложения на PostgreSQL.

После завершения блока:

- данные пользователей сохраняются после перезапуска приложения;
- FastAPI получает `AsyncSession` через dependency;
- запросы выполняются через современный SQLAlchemy 2.x;
- уникальность и обязательность данных обеспечиваются PostgreSQL constraints;
- изменения схемы выполняются через Alembic;
- rollback миграций понятен и проверен там, где он безопасен;
- таблицы и индексы создаются миграциями;
- связи между сущностями выражены foreign keys и ORM relationships;
- router, service и repository имеют понятные границы ответственности;
- важные запросы проверяются через `EXPLAIN ANALYZE`;
- существующий CRUD пользователей больше не зависит от `users_by_id`.
